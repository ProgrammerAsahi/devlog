上面这段话，是我的 RTX 4090 说的——准确地说，是跑在它上面的 Qwen3-1.7B 通过 vLLM 的 OpenAI 兼容接口，一个 token 一个 token 流式吐出来的（它先在`<think>`里打了半天草稿，然后才落笔）。落款那个 `[你的名字]` 是模型自己留下的占位符，我原样保留：这是 1.7B 小模型的天真，也是这篇日志的第一份真实。

为了让它说出这段话，我花了两天，闯了五关。

## 起点与环境

- Windows 11 + WSL2（Ubuntu 24.04，内核 6.18）
- RTX 4090，驱动 615.65（CUDA 13.4）
- uv 建的 Python 3.12 虚拟环境：torch 2.13、vllm 0.29
- 目标：`vllm serve Qwen/Qwen3-1.7B`，然后 curl 一次流式请求

听起来一步到位。实际上：

## 第一关：UVA is not available

`RuntimeError: UVA is not available`——报错文案有误导性。真相是 vLLM 0.29 的新 V2 Model Runner 需要一块 GPU 能直接读写的 pinned memory 中转缓冲区，而 vLLM 在 WSL 上默认禁用 pinned memory（历史原因：老 WSL2 内核支持不完整）。修法是一个环境变量：`VLLM_WSL2_ENABLE_PIN_MEMORY=1`。

## 第二关：GPU 人间蒸发

排查第一关时发现 `nvidia-smi` 直接报 *"GPU access blocked by the operating system"*，`torch.cuda.is_available()` 返回 False——WSL 根本看不到显卡了。`dmesg` 里躺着一次 dxg（WSL 的 GPU 准虚拟化通道）内核崩溃。修法在 Windows 侧：`wsl --shutdown`，重新进入。

## 第三关：Python.h 不存在

这次错误埋在几百行 traceback 的上面：`fatal error: Python.h: No such file or directory`。vLLM 默认用 `torch.compile` → Inductor → Triton，而 Triton 首次运行要用 gcc **现场编译**一个 C 扩展，需要 Python 开发头文件。Ubuntu 里它在单独的包里：`sudo apt install python3.12-dev`。

## 第四关：一台机器，三个 CUDA（最抓狂的一关）

FlashInfer 的采样 kernel 是 JIT 的：首次调用才现场编译，结果 nvcc 报错 `Unknown option '--compress-mode=size'`——这个参数 CUDA 12.8 之后才认识，而我系统里 apt 装的 nvcc 是 12.0。

排查后发现我的机器里同时跑着**三个版本的 CUDA**：驱动 13.4（Windows 映射进 WSL）、apt 的 nvcc 12.0、venv 里 pip 装的 nvcc 13.4。当时确实有点抓狂——没想到起步配环境比想象复杂这么多。

把编译指向 venv 的 nvcc 13.4 之后，又撞上更深一层：pip 包自己在"内战"——nvcc 是 13.4，但同目录的 CUDA 头文件标着 13.0，CCCL 的严格版本对检直接 `#error` 拒绝编译。

## 第五关：彻底修好，而不是绕过去

我选择把环境一次修对：删掉 apt 的 12.0，从 NVIDIA 官方 WSL 源安装自洽的 `cuda-toolkit`——顺便学到：WSL 源里当时根本没有 13.4，最高 13.3，**教程里的版本号会过期，`apt-cache policy` 查到的才是事实**。最终三层各归其位：驱动（13.4）不动、编译工具链统一为 `/usr/local/cuda-13.3`（`CUDA_HOME` 写进 `~/.bashrc`）、torch 的 pip 运行时视为私有依赖不去碰。

之后 `vllm serve` 一次通过：torch.compile 20 秒、CUDA Graph 录制 3 秒、FlashInfer 用新 nvcc 编译 49 秒，17.03 GiB 显存化作 **159,424 个 token 的 KV cache**——`Application startup complete`。

## 最值钱的一课

碰到失败和一长串报错，别慌。真正的根因常常只有**简洁的一行**，而且往往不在 Python traceback 里——在编译器自己的输出里。这四关我用了同一个手法四次：先按级别筛出 ERROR，再往 ERROR 块里找工具自己说的话（gcc 的 `fatal error`、nvcc 的 `fatal`、CCCL 的 `#error`）。定位到最深层的错误位置，根因基本就在那里。

## 预测 3 小时，实际 4.5 小时

值。最难搞的 CUDA 环境问题被一次性解决，以后不必再花时间；亲手写的总结和体会也更有参与感。万事开头难，走得慢一点，反而记得更深。

## 关于"AI 导师 + 我动手"这种学法

这次全程是 AI（Kimi-K3）当导师、我来执行。效率极高——同样的问题自己排查可能要花非常久。但代价也真实存在：错误不是我亲手发现的，记忆可能不够深。所以下一个任务开始，边界要往前挪一步：**排查问题也要被引导着做，而不是被替着做**。这是我和 AI 导师的新约定，写在这里，立字为据。

## 第一个 token 与那封信

说实话，第一个 token 蹦出来时，我高兴，但没那么兴奋——之前给部署在 Nebius token factory 上的 DeepSeek-R1 做前端整合时，已经见识过流式输出。但这次不一样：从驱动到工具链的每一层，是我自己（和导师一起）打通的。

不过说实话，把这封信重读了一遍，我的第一反应是觉得有点好笑。我都是成年人了，它写的东西仿佛我还是个啥都不懂的小婴儿——而且这口气听着像我爹。它还擅自用起了爸爸给儿子写信的口吻，我就这么喜获了一个"赛博小爹"。被它这么占便宜，想到这里还有点不爽，哈哈哈。而且用词确实过于文艺和矫揉造作了。不过想到这只是一个缺乏上下文的小模型写出来的，我也就释怀了——看着自己亲手搭起来的模型，写出这么一段辞藻甚至过于华丽的文字，喜悦还是超过了一切。

小模型也给我上了一课：1.7B 已经算"很小"，3.78 GiB 的权重还是要下一分多钟，前置依赖文件一大堆——大模型是真的大。我也第一次亲身感受到，CUDA 对大模型部署而言是命脉级的存在。

## 写给同路人

别被各种你不熟悉的名词、还有复杂的环境配置吓到。你不用一上来就懂或者记住这些东西，后面都会慢慢学会、记住的。**只要让模型成功部署、并且输出东西了，你就已经成功迈出了第一步。**
